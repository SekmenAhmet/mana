# Releasing mana

Two human decisions, everything else is machinery.

```
        HUMAN                      ROBOT

  PR into develop  ──────────────────────────────►  CI: 4 checks
        │
        │  (work accumulates on develop)
        ▼
  PR develop → main  ────────────────────────────►  CI: 4 checks
        │                                                │
        │                                                ▼
        │                                     release-plz opens/updates
        │                                     a Release PR on main:
        │                                     version bump + CHANGELOG.md
        ▼                                                │
  merge the Release PR  ◄────────────────────────────────┘
        │
        └──────────────────────────────────────►  release-plz pushes tag vX.Y.Z
                                                         │
                                                         ▼
                                                  cargo-dist builds 5 targets
                                                  + 2 installers, creates the
                                                  GitHub Release, uploads

                                                         │
                                                         ▼
                                                  `mana upgrade` and the launch
                                                  notice read that Release
```

**Human steps — exactly two:**

1. Open and merge the `develop → main` pull request. This is the "we are
   releasing" decision. Four required checks must pass, same as any PR.
2. Merge the Release PR that release-plz opens on `main`. This is the "this
   version, these notes" decision — read the changelog diff before merging;
   it is the last point at which the version number can be argued with.

**Robot steps — everything else:** reading the conventional commits, choosing
the semver bump, writing `CHANGELOG.md`, opening the Release PR, pushing the
tag, building five targets, generating the installers, creating the GitHub
Release, uploading the artifacts.

Nothing releases on `develop`. Nothing releases because a branch was pushed.
No tag is ever created by hand.

---

## The pieces

| File | Owns |
| --- | --- |
| `release-plz.toml` | version bump, `CHANGELOG.md`, Release PR, the tag |
| `.github/workflows/release-plz.yml` | when release-plz runs (push to `main`, nowhere else) |
| `dist-workspace.toml` | targets, archive format, installers |
| `.github/workflows/release.yml` | **generated** by cargo-dist, plus hand-added/hand-hardened bits |
| `src/cli/upgrade.rs` | the client side: `mana upgrade` and the launch-time notice |

`.github/workflows/release.yml` is regenerated by `dist generate`, so nothing
in it should be edited by hand — with two deliberate exceptions.

The first is the `guard` job at the top. dist has no way to express "refuse a
tag that is not on `main`", and without it any hand-pushed tag ships a release
from a commit CI never saw. It also refuses a tag whose *name* is not a
well-formed version (`v<major>.<minor>.<patch>` with an optional pre-release
suffix), checked with a shell `grep` against `$GITHUB_REF_NAME`, not a
`${{ }}` expression (see below for why that distinction matters). Re-add both
checks after any `dist generate`; `guard` is the first job in the file and
`plan` depends on it, which is what gates every other job.

The second is that every `run:` step which needs the tag reads it from an
`env:` binding (`TAG` / `TAG_FLAG`) as a quoted shell variable, instead of
`dist generate`'s default of interpolating `${{ github.ref_name }}` or
`${{ needs.plan.outputs.tag* }}` straight into the script. This workflow holds
`contents: write` and runs on a tag anyone can push, so a raw `${{ }}`
expression in a `run:` block turns an attacker-chosen tag name into shell
source text (mana issue #176) — GitHub's own documented remedy is the `env:`
indirection this uses instead. `dist generate` does not know about this either
and will put the raw interpolation back in the `plan`, `build-local-artifacts`,
`build-global-artifacts` and `host` jobs; re-apply the `env:` binding (and,
for `build-local-artifacts`, the explicit `shell: bash` its Windows runner
needs to make `$TAG_FLAG` resolve) after any `dist generate`.
`release_workflow_does_not_interpolate_tag_derived_expressions_in_run_blocks`
in `src/cli/upgrade.rs` fails if either regenerated job loses its `env:`
binding.

Both exceptions are why `dist-workspace.toml` carries `allow-dirty = ["ci"]`:
`dist generate --check` compares the whole file and would otherwise fail the
`deps & coverage` job on the hand edits alone. The cost is that config drift
(`dist-workspace.toml` edited without regenerating) is no longer caught
automatically — run `dist generate` yourself after touching that file.

## What ships

Five targets, one archive each, `.tar.gz` everywhere:

```
mana-aarch64-apple-darwin.tar.gz
mana-x86_64-apple-darwin.tar.gz
mana-x86_64-unknown-linux-gnu.tar.gz
mana-aarch64-unknown-linux-gnu.tar.gz
mana-x86_64-pc-windows-msvc.tar.gz
```

plus a `.sha256` beside each, an aggregate `sha256.sum`, `source.tar.gz`, and
the two installers `mana-installer.sh` / `mana-installer.ps1`.

`.tar.gz` on Windows too, where cargo-dist would default to `.zip`: `mana
upgrade` unpacks these with `self_update`, whose feature set here is
`archive-tar` + `compression-flate2`. One format means one code path. The
alternative was adding the `zip` crate to the audit surface for one platform.

Each archive unpacks to a directory, not a flat set of files:
`mana-<target>/mana`. `src/cli/upgrade.rs` knows this, and a test asserts the
names and the layout against a *recorded* `dist plan` run — change
`dist-workspace.toml` in a way that would break `mana upgrade` and the test
fails first.

No test runs `dist`; the recording is a hand-copied list, pinned to the dist
version it was taken from. So **bumping `cargo-dist-version` is a two-step
edit**: change the version in `dist-workspace.toml` *and* the installer URL in
`ci.yml`, then re-run `dist plan` and re-copy its artifact names into
`DIST_PLAN_ARTIFACTS`. `recorded_dist_plan_is_still_the_pinned_dist` fails until
you do — that is the only thing standing between a dist that renames archives
and a `mana upgrade` that cannot find the binary.

## Decisions, and why

**release-plz runs on `main` only.** It opens its Release PR against whatever
branch was checked out, so restricting the workflow trigger (`on: push:
branches: [main]`) is what restricts the branch. There is no
`release_branches` option; the trigger is the mechanism.

**`git_only = true`.** mana is `publish = false` and has never been on
crates.io. Without this, release-plz asks the registry what the current version
is, gets nothing, and treats every run as a first release. Git-only mode reads
the version from the `vX.Y.Z` tags instead — which is also why the workflow
checks out with `fetch-depth: 0`.

**`release_always = false`.** release-plz only cuts a release when the merged
commit came from one of its own `release-plz-*` branches. This is what keeps
the `develop → main` merge from releasing anything on its own — with the
default (`true`), the first such merge would tag and ship `v0.1.0` immediately,
because no `v0.1.0` tag exists yet.

**`git_release_enable = false`.** cargo-dist creates the GitHub Release and
fills its body from the `CHANGELOG.md` section release-plz just wrote. If both
tools created it, one of them would fail with a 422.

**Branch protection is not in the way.** `release-plz release` pushes *a tag*,
never a commit to `main`; rulesets protect branches. The Release PR's commit
goes through GitHub's GraphQL API onto an unprotected `release-plz-*` branch
(which also makes it show up as Verified). Nothing here needs a protection
bypass on `main`.

**A GitHub App token is not optional.** This is the one thing that will break
silently if it is skipped, and it breaks twice:

- A pull request opened with the default `GITHUB_TOKEN` does **not** trigger
  `on: pull_request` workflows. The Release PR would sit there with four
  required checks that never report and could never be merged. The deadlock is
  silent — the PR just never becomes mergeable.
- A tag pushed with the default `GITHUB_TOKEN` does **not** trigger other
  workflows. `release.yml` would never start and no artifact would ever be
  built.

Both jobs therefore mint a short-lived App token with
`actions/create-github-app-token`.

## What Ahmet has to configure on GitHub — checklist

Nothing in this repo can do these. Until they are done, the flow stops at the
Release PR.

- [ ] **Default branch is `main`.** Settings → General. release-plz and the PR
      UI both assume the release branch is the default one.
- [ ] **Create a GitHub App** (Settings → Developer settings → GitHub Apps →
      New). Name it something like `mana-release`. Under *Webhook*, **uncheck
      Active**. Repository permissions:
      - Contents: **Read and write**
      - Pull requests: **Read and write**
      - Administration: Read and write — **only if** a tag ruleset restricts
        tag creation (see below)
- [ ] **Generate a private key** for the App and **install the App on
      `SekmenAhmet/mana`**.
- [ ] **Add two repository secrets** (Settings → Secrets and variables →
      Actions):
      - `RELEASE_PLZ_APP_ID` — the App's ID
      - `RELEASE_PLZ_APP_PRIVATE_KEY` — the whole `.pem`, including the BEGIN
        and END lines
- [ ] **Allow Actions to create pull requests.** Settings → Actions → General
      → Workflow permissions → check *Allow GitHub Actions to create and
      approve pull requests*. Leave the token permission on *read-only*: the
      workflows declare what they need per job.
- [ ] **Tag rulesets, if any.** If a ruleset targets `refs/tags/v*` with
      *Restrict creations*, add the App to its **bypass list**. If there is no
      tag ruleset, nothing to do. Do not weaken the `main` ruleset — it is not
      what blocks anything here.
- [ ] **Do not add `CARGO_REGISTRY_TOKEN`.** Nothing publishes to crates.io,
      and a token sitting there is a way for that to change by accident.

Optional, but it makes the release commit readable: Settings → General → Pull
Requests → *Default to PR title for squash merge commits*.

## First release

The repo has no `v*` tag yet, so the first run has a wrinkle worth knowing
about.

1. Land this branch, merge `develop → main` as usual.
2. release-plz sees no tag matching `v{{ version }}` and treats the next
   release as the initial one. It opens a Release PR; read what version it
   proposes.
3. If it proposes something other than what you want, say so by pushing the
   baseline tag by hand *once*, **from a commit on `main`** —
   `git checkout main && git tag v0.1.0 && git push origin v0.1.0` — and let
   the next push to `main` re-open the PR from that baseline. This is the only
   tag anyone ever creates by hand, and it exists to give the robot a starting
   point. Tag anything else and `release.yml`'s `guard` job refuses the run:
   the tagged commit has to be an ancestor of `main`.

Note that `CHANGELOG.md` does not exist yet either. release-plz creates it on
the first Release PR, with the header configured in `release-plz.toml`; it is
deliberately not seeded here, because a file that already exists keeps its own
header and the configured one would never be used.

## After a release

`main` now carries a version bump and a `CHANGELOG.md` that `develop` does not.
Merge `main` back into `develop` (a PR, like everything else), or `develop`
will keep proposing a version that has already shipped.

## Trying it without releasing anything

```sh
dist plan                 # what the tag would build, without building it
dist build --target <t>   # one target, locally
dist generate --check     # is release.yml still what the config implies?
```

`dist` is cargo-dist's binary; install it with `cargo install cargo-dist
--locked` (the crate is `cargo-dist`, the binary is `dist`). The version must
match `cargo-dist-version` in `dist-workspace.toml` — a different version
generates a different workflow, and CI's drift check will say so.

release-plz can be rehearsed the same way: `release-plz update --dry-run`.

## The client side

`mana upgrade` downloads the archive for the running target from the newest
GitHub Release and replaces the running binary.

`mana launch` — and only `mana launch` — also checks, on a background thread,
whether a newer release exists, and prints one line into the chat pane if so:

```
* [mana] mana 0.2.0 available -- run `mana upgrade`
```

Never blocking, never fatal, silent when offline. The answer is cached in
`~/.mana/update-check.json` for 24 hours, so at most one request a day.
`MANA_NO_UPDATE_CHECK=1` turns it off entirely.

`mana ps` and `mana kill` never touch the network. Two neighbours that used to
be listed here do not qualify, and saying so is cheaper than a surprise:

- `mana doctor` runs each catalogue entry's own discovery command (`agy
  models`, `opencode models` today) to report a live model list, and those
  answer over their CLI's network. It issues no request of mana's own, which is
  a different claim from making none.
- `mana mcp-server` is a protocol server on stdio, so a stray HTTP request from
  *its* process would be a defect — but the sub-agents it spawns are agent CLIs
  talking to their providers, which is the entire point of them.
